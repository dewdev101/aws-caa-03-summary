Networking & VPC

CIDR / Subnetting พื้นฐาน

จำนวน IP ในบล็อก = 2(32 - prefix) เช่น /24 = 28 = 256 ตัว

  • Octet = กลุ่ม 8 บิต (4 octet รวมเป็น 32 บิต ของ IPv4)
  • Subnet mask บอกว่า octet ไหน "fix" (เครือข่าย) และ octet ไหน "แก้ไขได้" (host)
  • AWS VPC/Subnet อนุญาตขนาดตั้งแต่ /16 ถึง /28 เท่านั้น
  • AWS reserve IP แรกเสมอ 5 ตัว ต่อ subnet (network address, VPC router, DNS, future use, broadcast)

กับดัก: /1 ไม่ valid เลย (นอก range), /16 valid แต่กินพื้นที่ VPC ทั้งหมดจนไม่เหลือให้ subnet อื่น

NAT Gateway vs Network ACL (NACL)

NAT GatewayNetwork ACL
ให้ instance ใน private subnet ออกเน็ตได้ (outbound) โดยไม่เปิดให้ถูกเข้าจากนอกFirewall ระดับ subnet — allow/deny traffic ด้วย rule เป็น stateless (ต้องเปิดทั้ง inbound/outbound เอง)

กับดัก: สองตัวนี้คนละหน้าที่กันเลย — NAT คือ "ทางออกเน็ต" ส่วน NACL คือ "กฎกรองทราฟฟิก" อย่าสับสนว่าใช้แทนกันได้

Elastic IP — คงอยู่ถาวรจนกว่าจะปล่อย

Elastic IP ไม่หายไปเมื่อ stop/terminate instance เอง — ต้อง release เองเท่านั้นถึงจะคืน IP กลับ AWS pool

กับดัก: ถ้าปล่อย Elastic IP ไว้โดยไม่ attach กับ instance ที่ running อยู่ จะถูกคิดค่าใช้จ่าย (idle charge)

Storage & Migration

Storage Gateway vs DataSync vs DMS

บริการใช้เมื่อ
Storage Gatewayต้องการ continuous/hybrid access จาก on-prem ไป S3-backed storage (File/Volume/Tape Gateway)
DataSyncย้ายไฟล์/object จำนวนมาก แบบรวดเร็ว อัตโนมัติ ครั้งเดียวหรือตามตาราง (ไม่ตระหนักเรื่อง schema)
DMSย้าย database ที่ตระหนัก schema/transaction — Full Load + CDC (Change Data Capture)

DMS CDC-only mode ยิงเข้า Kinesis Data Streams ได้ ใช้แก้ปัญหา RDS ที่ไม่มี native stream

หลักจำ: ไฟล์ล้วนๆ จำนวนมาก → DataSync | มี schema/transaction → DMS | ต้องเข้าถึงต่อเนื่องจาก on-prem → Storage Gateway

Database

RDS Performance Insights — ลดค่าใช้จ่ายช่วงไม่ใช้งาน

Performance Insights ใช้ได้เฉพาะตอน instance กำลัง run อยู่ (ไม่ใช่ snapshot)

วิธีถูก: Snapshot → Terminate instance (หยุดจ่าย compute) → Restore จาก snapshot ตอนจะใช้งานจริง

กับดัก: mysqldump ไปวิเคราะห์บนเครื่อง local — เสีย Performance Insights ไปเลย และ environment ไม่เหมือนจริง

"Restart" = instance เดิมที่ยังมีอยู่ | "Restore" = สร้าง instance ใหม่จาก snapshot หลัง terminate ไปแล้ว

DynamoDB Global Table vs Global Secondary Index

Global TableGlobal Secondary Index (GSI)
Replicate ข้าม region — ใช้สำหรับ DRIndex เพิ่มเติม region เดียวกัน — ไม่เกี่ยวกับ DR

กับดักชื่อคล้าย — "Global" ใน GSI ไม่ได้แปลว่า multi-region

Compute & Messaging

Multi-AZ Fault Tolerance (สูตรคำนวณ)

ถ้าโจทย์บอก "ต้องมี X instance running ที่ at all times" แม้เสีย AZ ใดไป 1 AZ — หมายถึง อย่างน้อย X (minimum) ไม่ใช่ total ไม่เกิน X

สูตรเช็ค: (รวมทุก AZ) − (AZ ที่มีเครื่องมากที่สุด) ≥ X จึงผ่าน

ตัวอย่าง ต้องการ 6: (2,2,2)=4 ไม่ผ่าน | (3,3,3)=6 ผ่าน | (6,6,0)=6 ผ่าน (แต่ไม่ best practice เพราะ AZ หนึ่งไม่ได้ใช้เลย)

SQS — Delivery Semantics

  • ReceiveMessage = ซ่อนข้อความชั่วคราว (visibility timeout) ไม่ได้ลบ
  • DeleteMessage = ลบจริงหลัง process สำเร็จ
  • Standard Queue = at-least-once — มีโอกาสซ้ำได้เสมอ ปรับ visibility timeout ได้แค่ "ลด" ความเสี่ยง ไม่ใช่ "กำจัด"
  • ต้องการ exactly-once จริง → ใช้ FIFO Queue (มี deduplication)

EBS vs Instance Store

EBS (Elastic Block Store)Instance Store
Network-attached, persistent — ข้อมูลอยู่แม้ stop/terminate instance (ถ้าไม่ตั้งลบ)Physically attached กับ host เดิม — ข้อมูลหายถ้า stop หรือ terminate (หรือ hardware ล้ม)

กับดัก: Instance Store เร็วกว่า (local disk) แต่ใช้เก็บข้อมูลที่ต้อง persistent ไม่ได้เด็ดขาด — เหมาะกับ cache/temp data เท่านั้น

IAM & Security

IAM User vs Role vs Policy

IAM UserIAM RoleIAM Policy
Identity ถาวร มี credential ติดตัวสิทธิ์ชั่วคราว ไม่มีเจ้าของตายตัว ใครก็ "สวม" ได้เอกสาร JSON กำหนดสิทธิ์ (attach ให้ User/Role/Group)

เมื่อไหร่ควรใช้ Role

  • AWS Service ต้องเข้าถึง Service อื่น (EC2 → S3, Lambda → DynamoDB)
  • Cross-account access (Account A ให้ Account B assume role เข้ามา)
  • Federation (user จากภายนอกไม่มี IAM identity)
  • IAM Identity Center (SSO) — เลือก Role ตอน login
  • Break-glass / elevated access ชั่วคราว
หลักจำ: เจอคำว่า "temporary", "cross-account", "service-to-service", "federation" → นึกถึง Role ก่อน

AWS STS (Security Token Service)

ออก credential ชั่วคราว (Access Key, Secret Key, Session Token) ที่หมดอายุอัตโนมัติ

STS รับ input ได้แค่ 3 แบบ:

  • SAML 2.0 assertion → AssumeRoleWithSAML
  • OIDC token → AssumeRoleWithWebIdentity
  • Caller ที่ authenticated แล้ว (มี IAM credential + สิทธิ์ sts:AssumeRole)

STS ไม่รู้จัก LDAP protocol เลย — เชื่อมตรงไม่ได้ไม่ว่าจะเป็น use case ทั่วไปแค่ไหน

Custom Identity Broker Pattern

ใช้เมื่อ identity store (เช่น LDAP) ไม่รองรับ SAML/OIDC

User → (LDAP auth) → Broker App → (AWS API ด้วย credential ของ broker) → STS → temporary credential → ส่งกลับ user

Broker ทำหน้าที่ "แปลภาษา" ระหว่าง LDAP protocol กับ AWS API

IAM Identity Center (ชื่อเดิม AWS SSO)

จุด login เดียวสำหรับเข้าหลาย AWS Account โดยไม่ต้องสร้าง IAM User แยกทุก account

  • Identity source — user จาก Identity Center เองหรือต่อ AD/Okta/Azure AD/Google Workspace
  • Permission Set — แม่แบบสิทธิ์ (เหมือน Policy template)
  • Account assignment — จับคู่ User/Group + Permission Set + Account

ต้องการ identity source ที่คุยผ่าน SAML/SCIM ได้ — ถ้า LDAP ไม่รองรับ SAML ต้องใช้ Custom Identity Broker แทน ไม่ใช่ Identity Center

Amazon Cognito (สำหรับแอปของบริษัทเอง ไม่ใช่ AWS Console)

  • User Pool — จัดการ user/login ด้วย email ออก JWT token ให้แอป backend เช็คสิทธิ์ตาม Group
  • Identity Pool — แลก token เป็น temporary AWS credential (ผ่าน Role) เพื่อให้ user เข้าถึง AWS resource ตรงๆ (เช่น upload S3 จาก mobile app)

IAM Role vs IAM Group

IAM RoleIAM Group
สวมได้ชั่วคราว ไม่มี credential ติดตัว ให้ service/คนนอก/คนละ account assume ได้แค่ "ตะกร้า" รวม IAM User หลายคนไว้ด้วยกัน เพื่อ attach Policy ครั้งเดียวให้ทุกคนในกลุ่ม

กับดัก: Group ไม่ใช่ identity ที่ assume ได้ และไม่มี credential ของตัวเอง — เป็นแค่ตัวจัดกลุ่ม User เท่านั้น

Lambda: Execution Role vs Resource-based Policy

Execution RoleResource-based Policy
สิทธิ์ที่ติดกับ Lambda function เอง — กำหนดว่า Lambda "ไปทำอะไรกับ service อื่นได้บ้าง" (เช่น เขียนลง DynamoDB)Policy แปะที่ Lambda — กำหนดว่า "ใครมีสิทธิ์เรียก Lambda นี้ได้บ้าง" (เช่น ให้ S3 event หรือ API Gateway เรียกได้)
หลักจำ: Execution Role = Lambda มองออกไปข้างนอก | Resource-based Policy = คนนอกมองเข้ามาที่ Lambda

Management & Monitoring

AWS CloudFormation (CFN)

Infrastructure as Code — เขียน template (YAML/JSON) แบบ declarative เพื่อ model/provision/version-control infra ทั้งหมดในไฟล์ text เดียว

เทียบได้กับ Kubernetes deployment.yaml แต่ CFN คุมทั้ง AWS account ส่วน K8s YAML คุมแค่ภายใน cluster

ข้อจำกัด: deploy stack ใหม่ตอนเกิด failure จริงช้ากว่า resource ที่ pre-provisioned ไว้ล่วงหน้า

CloudWatch Logs — Compliance Auditing

Unified CloudWatch Logs Agent รองรับทั้ง Windows + Linux เก็บรายละเอียดระดับ system (memory, disk, process) เกินกว่า metric ระดับ hypervisor ปกติ

วิเคราะห์ log ด้วย CloudWatch Logs Insights (query ภาษาคล้าย SQL)

AWS Inspector = security scanning (ผิดจุดประสงค์) | SSM Agent = remote management (ผิดจุดประสงค์) | Custom SDK script = effort สูงเกินจำเป็น

เครื่องมือดู log อื่นๆ: OpenSearch Service, QuickSight, และนอก AWS เช่น Datadog, Splunk, Grafana+Loki, ELK Stack

DR & Resilience

Multi-region DR Architecture

  • DynamoDB Global Table สำหรับ replicate ข้าม region (ไม่ใช่ GSI)
  • Route 53 DNS Failover สำหรับสลับ traffic ไป secondary region
  • AWS Well-Architected Tool สำหรับ architectural review + best practices (ไม่ใช่ Compute Optimizer ที่ทำแค่ rightsizing, ไม่ใช่ Prometheus/Grafana ที่ทำแค่ metrics/dashboard)

Governance & Org

Service Control Policy (SCP) vs AWS Control Tower

SCPAWS Control Tower
Policy ที่ใช้ "จำกัดเพดานสิทธิ์สูงสุด" ของทุก account ใน AWS Organizations (แม้เป็น root user ก็ทำเกิน SCP ไม่ได้)บริการที่ตั้ง multi-account landing zone ให้อัตโนมัติ — สร้าง OU, account, guardrail (ซึ่งหลายตัวสร้างจาก SCP ให้) และ account vending

กับดัก: SCP คือ "เครื่องมือ" กำหนด guardrail ส่วน Control Tower คือ "ระบบจัดการ" ที่ครอบ SCP + อื่นๆไว้อีกชั้น ไม่ใช่สิ่งเดียวกัน

API & Edge

API Gateway Custom Domain + ACM Certificate Region

Edge-Optimized EndpointRegional Endpoint
Certificate (ACM) ต้องอยู่ที่ us-east-1 เท่านั้น (เพราะไปผ่าน CloudFront ด้านหลัง)Certificate ต้องอยู่ region เดียวกับ API Gateway นั้นๆ (เช่น API อยู่ us-east-2 → cert ต้องอยู่ us-east-2 ด้วย)

กับดัก: หลายคนจำว่า ACM ต้องอยู่ us-east-1 เสมอ (จริงสำหรับ CloudFront/Edge-optimized) แต่ถ้าใช้ Regional endpoint ต้องอยู่ region เดียวกับ API เอง

หลักจำ: Edge-Optimized = ผ่าน CloudFront → cert ที่ us-east-1 | Regional = cert ตาม region ของ API Gateway นั้นเลย
